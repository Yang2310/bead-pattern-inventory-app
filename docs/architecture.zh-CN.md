# 架构与工程设计

[English](architecture.md) | **简体中文**

## 系统职责边界

微信小程序负责用户交互与界面状态；Python/FastAPI 后端负责请求校验、图纸与库存业务规则、数据持久化。前端通过 REST API 与服务端通信，不直接访问 MySQL 业务库。

    微信小程序界面
       | HTTPS / JSON REST
       v
    FastAPI 路由 / 校验 / 业务服务
       |---------------------|
       v                     v
    MySQL                 腾讯云 COS
    - 图纸元数据           - 长期参考图片
    - 结构化网格           - 上传图片资源
    - 进度与状态
    - 库存与流水

部分用户提交的文本、图片还会经过微信内容安全接口。生产凭据和环境私密配置不在本公开仓库中。

## 两条图纸数据流程

**制作图纸：** 普通图片 -> 颜色处理与匹配 -> 结构化拼豆网格 -> 编辑/预览 -> 保存网格及进度。后续可根据结构化数据重新展示或修改图纸。

**导入已有图纸：** 上传图纸图片 -> 裁剪、网格检查以及必要的人工校准 -> 参考图片与进度 -> 保存裁剪主图和相关元数据。这里不能理解为“自动识别全部豆号”。

两条流程复用图纸管理和库存概念，但长期保存的媒体内容并不完全相同。

## 库存流水与一致性

图纸操作能否改动库存由后端业务规则决定。库存流水与相关图纸操作建立关联，涉及已完成区域增量同步、完成、重新开始及删除等场景；需要避免同一库存变更被重复扣减。这里描述的是已有设计和实现，不是对全部并发场景给出形式化证明。

## 实际排查过的数据库问题

原先图纸列表查询包含体积较大的结构化 JSON 字段，曾触发 MySQL 排序内存错误。项目调整为延迟加载该字段，让列表读取轻量级元数据，需要查看/编辑图纸详情时再获取完整结构化内容。

## 部署边界

项目曾使用自建环境部署；代码中提供 Docker Compose、Nginx 与健康/就绪检查支持，但完整代码和配置仍在私有仓库。目前不承诺持续在线的公开可访问 Demo。
